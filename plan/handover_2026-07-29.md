## Issue #7 -- implemented (self-describing ONNX)

Design decision after reviewing the config-contract WIP: **two serialization
schemes on purpose.**

- `config_resolved.yaml` stays the human training/eval schema
  (deg-denominated, parsed by `train_mappo.build_env_config`). It is LOSSY:
  it cannot express `RaycastConfig` (n_rays/fov/max_range/two_channel),
  `k_neighbours`, or `head_limit` -- fine while all runs use default rays/K,
  but never a deployment payload. Follow-up candidate: a guard in
  `cfg_dict_from_env_config` that raises when non-defaults would be dropped.
- `crowdrl_core.config_io` is the new lossless boundary (asdict/JSON, raw
  radians, nested raycast). Missing keys fill from defaults (new fields are
  default-off and post-date the artefact); unknown keys raise (the run used a
  feature this core cannot reproduce). The `crowdrl.*` metadata key names
  live here; exporter and reader both import them.

Write side (`crowdrl_train.export.export_onnx`): optional
`obs_config`/`action_config` (both or neither) + `provenance` dict ->
`metadata_props` (`crowdrl.schema_version` = "1", obs/action config JSON,
obs/action dims, provenance). Refuses to export when `obs_config.obs_dim`
contradicts the actor input width. Wired in `train_mappo.py` (run id + git
rev provenance) and the notebook 06 export cell.

Read side (`crowdrl_jupedsim.policy`): `OnnxPolicy.metadata`
(`PolicyMetadata`) parsed at load with cross-checks (corrupt/partial record,
unknown schema version, recorded obs_dim vs graph width, reconstructed vs
recorded width). `resolve_configs` decision table: metadata-only ->
self-configure; metadata + explicit -> field-for-field agreement or raise
(kills the nogoaldir same-width landmine); legacy artefact -> explicit
configs required + "unverified" warning; `ConstantPolicy` silent. The
resolved ObsConfig must derive the policy's actual input width -- handover
2026-07-20 finding 5 (silent `ObsConfig()` default saturating goal-dir at
+/-10) is closed. `LearnedPolicyModel` no longer defaults configs.

The package `__init__` imports the model classes lazily (PEP 562) so the
jupedsim-free surface (`OnnxPolicy`, `resolve_configs`) imports in CI; the
end-to-end contract test (`tests/test_config_metadata_roundtrip.py`, real
torch export -> deployment reader) runs there.

Legacy artefacts (`policy_r0400/r0800.onnx` etc.) deploy via explicit
configs rebuilt from `config_resolved.yaml` and warn. Parked: re-export the
best checkpoint with embedded metadata and ship it in the repo.

## Adapter on jupedsim 2.0

- `4c09c25` port: `final_target`/`next_target` + `EnvironmentQuery`
  (containment via `inside_geometry`; the cached shapely polygon path is
  gone). Plan v8 3.2/3.6 passages corrected (the stale `ped.target` claims).
- `f04aa37` navigation: `WorldState.route_next_waypoints` -- an external
  router's per-agent next waypoint. Both obs builders prefer it over a
  navmesh query; `path_deviation` = 0.0 under the single-waypoint contract
  (bounded, in-distribution: normalizes to -0.37 sigma per the baked stats;
  the behavioural reliance on rare p_dev spikes remains an open ablation).
  Also fixed: `use_navmesh=True` with neither source silently DROPPED the 3
  dims (89D config -> 86D obs); a route now fills them.
- `dfae80a` temporal memory: `TemporalMemory` on `CrowdRLAgentState`,
  replicating CrowdEnv exactly (slots pre-filled with spawn values;
  post-step, post-containment position written at the PRE-step count's slot;
  count incremented after). Lazy init on first `compute_next_state` -- spawn
  and routed goal are unknowable at `add_agent` time. Buffers are
  copy-on-write; the state object is shared live with the simulation.

### Known caveats (documented in code comments)

1. Neighbour temporal rows in `build_world_state` are indexed with the EGO's
   step count; buffers of agents added at different times would misread.
   Harmless until `use_neighbor_trajectory_features` (A++) is wired --
   per-agent read indices needed then.
2. Contact forces remain absent (walking-skeleton scope): agents can
   interpenetrate; JuPedSim contributes no collision resolution.
3. `check_model_constraint` is not overridden; JuPedSim's default constraint
   throwing still applies.

## Done later the same day

- **r0400 re-export shipped.** `scripts/reexport_onnx.py` rebuilds actor +
  frozen normalizer from a checkpoint + `config_resolved.yaml` and exports
  with embedded metadata. `example_model/policy_r0400.onnx` (gitignore
  exception added) is **bit-exact** vs. the run's original artefact
  (max |diff| 0.000e+00 on 256 random inputs) and self-configures:
  `LearnedPolicyModel(OnnxPolicy(path))`, nothing else.
- **Bottleneck scenario: crowd behaviour translates, with one caveat.**
  12 agents through a 1.4 m aperture (self-configured r0400): 12/12 exit in
  12.0 s sim (first 4.7 s, median 6.5 s, last 12.0 s; specific flow ~1.2
  (m s)^-1, near the empirical bottleneck range). The corner also passes
  with r0400 fully self-configured (4/4, 12.1 s). **Caveat:** min pairwise
  distance in the neck hit **0.044 m** -- near-total interpenetration for a
  moment. Navigation and throughput translate; spacing discipline in the
  squeeze does not, because contact forces are not wired in the adapter
  (caveat 2 above). Wiring the shared crowdrl-core contact-force module into
  the adapter integration is the natural next physics step; the e2e test
  documents but deliberately does not assert on spacing until then.
  All three scenarios live in `tests/test_e2e_jupedsim_trained_policy.py`;
  the self-configured ones need no environment variables.

- **Contact physics wired (Option A).** User observed agents' centres
  reaching the walls (zero-radius behaviour) in the notebook animation --
  correctly diagnosed as OUR walking-skeleton gap, not jupedsim (which never
  resolves collisions for operational models). `LearnedPolicyModel` now takes
  `walkable_geometry` (the same shapely Polygon given to `jps.Simulation`)
  and, when provided, runs the training env's exact physics per step, in the
  exact crowd_env.step order: contact accelerations (crowdrl-core
  `compute_contact_forces`, stiffness 30000 / damping 500 defaults) on
  pre-integration positions with post-filter velocities -> `v += a*dt` ->
  magnitude clamp -> integration -> `enforce_wall_boundaries` (body clearance
  = max(shoulder, chest) = 0.225 m default). Inherent approximation of the
  per-agent callback contract: neighbours are one step stale for the ego's
  force computation. Without the argument the old centre-point containment
  runs and construction WARNS. Results: wall clearance holds (>= 0.225 m
  everywhere, e2e-pinned); bottleneck min pairwise distance 0.289 m (was
  0.044 m -- head-on body contact is 0.30 m); 12/12 still exit but in ~30 s
  (was ~12 s of ghosting): a real queue forms, and the resulting throughput
  sits BELOW the empirical bottleneck range -- a policy-behaviour finding
  (yielding / dense packing, consistent with the known high-density
  weaknesses), not an adapter gap. Follow-up candidate: contact/dynamics
  params (stiffness, damping, desired_velocity_weight, max_velocity_magnitude)
  are env-level config that does NOT travel in the #7 metadata (schema v1
  covers obs+action only) -- consider a schema v2 embedding the dynamics
  block so deployment cannot drift on physics constants either.
