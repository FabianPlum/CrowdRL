## Blocking findings

**1. `agent.destination` is not exposed to Python.** This is the big one.

- `StrategicalDecisionSystem` sets `agent.target` = final stage target (exit centroid).
- `TacticalDecisionSystem` then sets `agent.destination` = routed next waypoint.
- All **seven** built-in C++ operational models read `agent.destination`. Zero read `target`.
- The Python binding (`python_bindings_jupedsim/agent.cpp`) exposes only
  `id, journey_id, stage_id, position, target, model`.

So the Python custom-model layer is the only model in the codebase handed the router's
*goal* instead of the agent's *waypoint*. Our adapter reads `ped.target` and consequently
points every agent at the exit through walls -- confirmed empirically: corner scenario,
0/20 agents exited, all pinned at the wall `y=2.0`.

Fix is a one-line binding addition upstream. Plan v8 Section 3.6 states JuPedSim supplies
"the route waypoint `ped.target`" -- wrong on both counts, **still needs correcting**.

**2. The trained example policy needs 89D; the adapter builds 80D.**

`example_model/policy_r0400.onnx`, input `['n_agents', 89]`:

| Block | Dims | Adapter status |
|---|---|---|
| ego | 8 | wired |
| social | 56 | wired |
| raycasts | 16 | wired |
| navmesh | 3 | **not wired** |
| temporal memory | 6 | **not wired** |

Its config has `use_goal_direction: false`, so the global goal bearing is zeroed and the
**next waypoint is the only navigation signal there is**. `destination` is not an
improvement over `target` for this checkpoint -- without it the policy has no navigation
input at all.

**3. Action config cannot be reconstructed at deployment.** The YAML->`ActionConfig`
mapping lives in `train_mappo.py:154` (`np.radians(act.get("max_heading_change_deg", 1.146))`)
-- a top-level script outside every package. For the example model that is
`radians(4.8) = 0.0838` rad/step vs the adapter default `0.020` -- **4.2x off**, and
silent. This is the strongest concrete justification for issue #7.

**4. `path_deviation` has no JuPedSim source -- but zeroing it is numerically safe.**
It needs a navmesh plus the final goal. We have the goal (`ped.target`); we lack the
navmesh, and building one means duplicating JuPedSim's router and pulling `triangle` back
into deployment. Under "only the next waypoint is ever available" it has no source.

The baked normalizer statistics (see below) de-risk this considerably: `p_dev` is bounded
below by 0 by construction, with training mean 0.040 and std 0.108, so feeding 0.0
normalizes to **-0.373** -- comfortably inside the training distribution, because "straight
path is clear" was the common case. This is *not* an out-of-distribution input. The open
question is narrower than first framed: purely whether the policy behaviourally relies on
the rare large spike (a sharp corner at p_dev=0.5 is +4.26 sigma). That is what the
ablation in next steps settles.

**5. The observation normalizer makes a config mismatch catastrophic and silent.**

The ONNX takes raw observations and applies frozen normalization internally
(`(x - mean) / std`, clipped to [-10, 10]). The baked buffers are an empirical record of
the training distribution:

| idx | dim | mean | std |
|---|---|---|---|
| 0, 1 | ego `goal_dir_x/y` | 0.000 | **0.0001** |
| 6 | ego `torso` | 0.000 | **0.0001** |
| 80 | nav `wp_dir_x` | 0.966 | 0.130 |
| 81 | nav `wp_dir_y` | 0.088 | 0.204 |
| 82 | nav `path_dev` | 0.040 | 0.108 |

`std = 1e-4` is the normalizer's epsilon floor -- those dims were *identically zero* for
the whole run, exactly as `use_goal_direction: false` guarantees. Consequence:

```
goal_dir_x = 1.0  ->  (1.0 - 0.0) / 0.0001  =  9999.9  ->  clipped to +10
```

**The adapter currently uses `ObsConfig()` defaults, where `use_goal_direction=True`.** So
deploying this checkpoint as things stand would drive indices 0 and 1 at a saturated +/-10
-- a maximal constant the network never saw -- with no error and no warning. This is
arguably more dangerous than the `destination` gap: `destination` fails *visibly* (agents
walk into walls), this fails silently.

Index 6 tells us torso was never actuated relative to heading in this run, while the head
clearly was (`std = 1.16`). Worth knowing before wiring the remaining blocks.

Also note `wp_dir` is nearly constant: mean magnitude 0.970, sitting 5.2 deg off the
heading axis with ~+/-12 deg spread. The policy servos its waypoint to straight-ahead, so
that input barely varies in practice. The 0.970 magnitude (vs 1.0 for a unit vector) also
shows the zeroed-fallback branch fired *rarely* during training.

## Other findings

- **`dt` silently rescales the motion envelope.** Action limits are applied per *step*, not
  per second: `max_heading_change = 0.020` rad/step is 115 deg/s at dt=0.01 but 23 deg/s at
  dt=0.05. Training and JuPedSim both default to 0.01. Our adapter tests were running at
  0.05 -- now pinned to 0.01. The adapter does not validate `dt` at all; a user passing
  `jps.Simulation(dt=0.05)` silently gets a policy at 1/5 its trained turn rate. Needs its
  own issue (distinct from #7: #7 is "config does not travel with the artefact", this is
  "a framework-supplied parameter changes the dynamics").
- **`metadata_props` on the example ONNX is empty** -- issue #7 confirmed unimplemented.
- **The exported graph is already batch-shaped** `['n_agents', 89]`. The batching work is
  entirely on the JuPedSim side; our export is ready.
- **Per-agent callback cost:** 20 agents x 20,000 steps = 986 s wall for 200 s sim time
  -- **0.2x real-time**, ~2.5 ms per agent-step.

## To clarify with the JuPedSim dev team

1. **Expose `agent.destination` on the Python `Agent` binding.** Framed as a gap, not a
   feature request: every C++ model gets the waypoint, the Python layer cannot. One line:
   `.def_property_readonly("destination", [](const GenericAgent& a) { return intoTuple(a.destination); })`
2. **Can the remaining route be exposed, not just the next waypoint?** Would supply
   `path_deviation`. The router already computes it. If the answer is a firm no, that is
   also useful -- it settles the observation design.
3. **A batch hook for operational models.** `compute_next_state` receives one agent and no
   handle on the population, and mutating simulation access during `iterate()` raises -- so
   batching cannot be worked around from our side. Our ONNX already accepts `['n_agents', 89]`.
4. **Is there a `dt` convention or validation expectation** for custom models, given
   per-step action limits?
